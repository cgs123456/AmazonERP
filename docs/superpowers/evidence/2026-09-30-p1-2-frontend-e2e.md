## 2. 根因（两条叠加）

1. 套件自称「连接本地真实后端栈」，但本地与 CI runner 都没有 16 个微服务在跑，`/api/*` 必然失败。
2. 本地还叠加系统代理：失败请求**挂住**而不是快速失败，于是 `waitForLoadState('networkidle')` 永不达成。

冷启动 vite 又叠加了首屏编译耗时，所以表现为「大面积超时」而非「快速报错」。

- Docker 拉镜像在本机不可用（docker daemon 代理 `127.0.0.1:7897` 已死），CI 上也没有后端服务。
- 打桩后单套件秒级到 2 分钟量级，具备进 CI 的条件。
- 桩数据是固定常量，**不含时间戳/随机值**，结果可复现（延续 Phase 0 确定性原则）。

## 4. 两条「假通过」用例的修正（重要）

这两条在旧套件里是绿的，但实际上什么都没测到：

1. **`Dashboard 交互 › KPI 卡片与图表区域渲染`**：原断言 `.kpi-grid` / `.chart-card` 存在。
   但**骨架屏里也有同名节点**，所以「数据永远加载不出来」时它照样通过。
   → 改为：先断言 `.skeleton-zone` 消失，再断言 4 张 KPI 卡与真实数值（`$12345.67`、`23`、`12.5%`、`$536.77`）以及 7 根趋势柱。
2. **`Dashboard 交互 › Agent 发送消息应收到回复`**：原断言「回复非空」。
   而 `/api/ai/chat-stream` 若按 JSON 兜底返回，`fetch` 拿到 200 但 `readSseStream` 解析不出任何事件，
   占位气泡永远是空串——页面看起来没坏，但也没回复。
   → 桩改为按 SSE 帧协议返回 `final` 事件，断言回复包含 `23 笔订单` / `$12,345.67`。

同时给 fixture 加了全局防护：捕获 `pageerror`，用例结束时若存在未处理异常即失败。
没有这条时，把页面打进渲染异常的 bug 会被「页面标题非空」这类弱断言放过。

## 5. 修掉的真实前端崩溃（不是测试问题）

`/report/dashboard/sales-trend` 的返回值被 `Dashboard#maxSales` 用 `for...of` 遍历。
后端（或桩）返回非数组时抛 `TypeError: salesTrend.value is not iterable`，
Vue 渲染中断 → **骨架屏永不消失、页面等于白屏**。

- 修复：`Dashboard.vue` 三组数据赋值前加 `Array.isArray` 防御，非数组退到 mock。
- 这属于产品健壮性问题，与打桩无关：后端字段变更/异常分支返回非数组就会触发。

## 7. 诚实边界（后人不得误读）

1. **打桩 ≠ 后端契约验证。** 这套测试只证明「前端拿到这样的响应会这样渲染/交互」，
   不证明后端真的返回这个结构。后端改字段名而前端未同步时，CI 仍然会绿——
   那是后端集成测试的职责，本套件不覆盖。
2. **视觉/截图断言不可靠。** 桩对外部域一律 abort，图标 CDN 不加载，所以用例只依赖文本与 DOM。
3. **桩只装在 fixture `page` 上。** 自建 `browser.newContext()` 的 4 条用例（all-pages 3 条、
   full-interaction 1 条）不带桩；它们目前只 goto `/` 或依赖路由守卫，不依赖 API。
4. **all-pages 的旧弱断言已在 §8 第二批打桩中逐条重写**（10 条，全部改为可失败的数值/条数断言）；
   full-interaction 中仍残留少量弱断言（"标题非空"之类），未逐条重写，列为后续项。
5. **耗时成本**：E2E 让 `frontend` job 从约 1 分钟增加到约 3 分钟（含浏览器安装）。
   若后续觉得慢，可把浏览器安装换成缓存或 `mcr.microsoft.com/playwright` 镜像，但不要用 skip 换绿。

## 8. 第二批打桩：广告 / 财务 / 选品 / 海外仓（2026-09-30 追加）

### 8.1 为什么 §3 的「未覆盖缺口」必须补，而不是留着

EMPTY_PAGE 兜底是 `{list,total,page,size}` 的**对象**形状。而这批页面里大量 `list*` 接口后端返回的是
**数组**（分页元数据在 `Result._page`，不在 `data`）：`/ad/reports`、`/ad/trend`、
`/ops/selection/opportunities`、财务凭证、海外仓入库/出库单等都是数组。

落到对象兜底时 `Array.isArray(res.data)` 为 false，前端静默走空态分支：**页面不报错、也不显示任何真实数据**。
这正是"测试绿了但其实什么都没测到"的来源——断言只要写"页面标题非空"就永远通过。
反向也危险：把对象形状塞给期望数组的字段，Vue 的 `v-for` 会去遍历对象的值，渲染出一堆无意义的行。
所以形状必须逐个对齐 `src/api/*.ts` 的泛型参数，不能靠兜底。

### 8.2 登记的 16 个端点

| 分组 | 端点 | 形状 |
|------|------|------|
| 广告 | `/ad/reports`、`/ad/trend`、`/ad/campaigns/list/{shopId}`、`/ad/creatives/list/{campaignId}`、`/ad/targeting/list/{campaignId}` | 数组 |
| 广告 | `/ad/campaigns/summary/type/{shopId}` | 对象 `Record<adType, AdSummary>` |
| 财务 | `/finance/voucher/list/{shopId}`（游标分页，两页）、`/finance/voucher/{id}/sync`、`/finance/profit/{shopId}` | 数组 / 对象 / 对象 |
| 选品 | `/ops/selection/opportunities`、`/ops/selection/market`、`/ops/selection/ai-suggestion/{id}` | 数组 / 对象 / 对象 |
| 海外仓 | `/logistics/warehouse/list/{shopId}`、`/logistics/warehouse/inventory`、`/logistics/inbound/list/{shopId}`、`/logistics/outbound/list/{shopId}` | 数组（后三个带 `_page`） |

为此给桩框架加了 `_page` 元数据字段（`size/returned/hasMore/truncated/nextCursor/total`），
否则"加载更多 / 截断提示"这类分页 UI 断言无处可依。

### 8.3 桩里必须复现的后端语义（不是塞个常量就完事）

| 语义 | 为什么必须在桩里实现 |
|------|--------------------|
| 财务凭证游标分页两页不同（第一页 `truncated=true` + `nextCursor=cursor-2`，第二页收口） | 单页桩会让"加载更多"按钮永远不出现，那条用例等于没跑 |
| `sourceType` 服务端过滤 | 后端按 `sourceType` 查库；桩若忽略参数，筛选用例只是重渲染同一批数据 |
| `/finance/voucher/{id}/sync` 返回 `status: 'MOCK'` | 必须区分"模拟调用成功"与"真的入账了"，前端据此给不同 toast 文案，断言的就是这个区分 |
| 广告数据刻意取整数（花费 500 / 销售额 2500） | ACoS 20.0% 与 ROAS 5.00x 可以手算出来写进断言，不需要复制运行时数字 |
| 数组 / 对象形状逐个对齐 `src/api/*.ts` 泛型 | 见 §8.1，形状错了要么静默空态，要么渲染垃圾行 |

### 8.6 反向验证：证明第二批桩是承重的

方法：把这 16 个端点的 `match` 前缀改成 `^/__off/`（共替换 16 处），让它们全部回落 EMPTY_PAGE 兜底，
再跑 `all-pages` + `full-interaction`。

| 轮次 | 结果 |
|------|------|
| 第一轮 | 14 failed / 25 passed（3.8m） |
| 第二轮（完整落盘） | **13 failed / 26 passed**（3.9m） |

其中**真实断言失败 11 条**，全部落在本次新增的分组上：

- 广告 3：all-pages「ACoS 概览」（`Expected "20%"` / `Received "整体 ACoS0%"`）、
  AdManager「SB tab 素材」「DSP tab 汇总卡片」
- 财务 4：all-pages「凭证 3 条 + 第二页」「利润 ¥12345.67」（`Received "¥0.00"`）、
  Finance「加载更多」「来源类型筛选」
- 选品 2：all-pages「2 条机会」、ProductSelection「关键词分析」（`Received "市场分析摘要：（） 非季节性"`）
- 海外仓 2：all-pages「仓库 + 入库单」、Warehouse「四个 Tab」

其余 2~3 条是**超时，且隔离复跑全部通过**，因此是降级运行下的负载假象，不是真依赖：

| 用例 | 批量跑 | 隔离复跑 |
|------|--------|----------|
| all-pages › Orders（桩未被禁用） | failed（Expected 3 / Received 0） | **1 passed（1.5s）** |
| full-interaction › 侧边栏跳 /finance | timeout 30s | **1 passed（8.9s）** |
| full-interaction › 侧边栏跳 /ads | timeout 30s | **1 passed（1.6s）** |
| all-pages › Notifications | timeout 30s | **1 passed（2.0s）** |

结论：去掉第二批桩后 11 条断言立刻变红 → 这批桩是 load-bearing 的，不是装饰。
两次批量跑的失败数不一致（14 vs 13）本身也说明降级状态下存在时序抖动。

### 8.7 由此暴露的一个真风险（未修，列后续项）

在"很多页面同时拿不到数据"的降级状态下，整轮耗时从 ~54s 涨到 3.8~3.9m，
部分用例（含**桩未被禁用**的 Orders）会撞 30s 用例超时而失败，隔离跑又是绿的。

这是**潜在的 CI flake 源**：CI runner 通常比本地慢（尤其首次冷启动 vite）。
可选缓解：给有数据依赖的用例单独加大 `test.setTimeout`、或把 `expect` 超时上调。

**远端观察（run `36646986161`）：该风险没有复现**——远端 `45 passed (25.3s)`，比本地（54s）还快。
因此当前不改阈值（不凭本地猜测动配置）。但这是**单次观察**，不是稳定性证明；
若后续在 CI 上真的出现超时失败，优先按上面的缓解项处理，而不是 skip。
