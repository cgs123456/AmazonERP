# P1-3 随访：风险 #2 —— order/V4 在大表上的耗时与并发影响（2026-09-30）

> **结论先行**：在 5,000,000 行 / 1.8 GB 的 `amz_order` 上，V4 原文一条 ALTER 实测
> **85.5 s**（同语义另一次 129.5 s）；时间几乎全花在两个 `ADD` 上（复合唯一键 ~40 s、复合索引 ~25 s），
> `DROP INDEX` 是元数据级操作（0.07–0.15 s）。**并发写入没有被阻塞**：DDL 跑到第 8 秒时从另一会话
> `INSERT` 实测 0.013–0.119 s；`ALGORITHM=INPLACE, LOCK=NONE` 被 MySQL 接受并跑完（rc=0）。
> 半迁移态再跑 V4 的 `1061` 在 5M 行表上**瞬间返回**（<1 s），不会「卡几十分钟才失败」。
> **但不要用单一数字外推**：同一条 SQL 在本机两次跑出 37.987 s 与 86.869 s（差 2.3 倍）。

## 1. 为什么之前是缺口、这次补的是什么

`2026-09-30-p1-3-risk2-order-v4-drop-index.md` 只证明了 V4 **不可重入**（1091）和半迁移态会撞 **1061**，
所有实验都在几行的空表上做。运维真正要问的两件事当时没有答案：

1. 库已经很大时，V4 要占多久（能不能塞进维护窗）；
2. 这期间会不会锁住写入。

本节用 5,000,000 行的同构 `amz_order` 补上这两项。**没有改动 V4，也没有改动任何生产对象。**

## 3. 方法

- 计时取自**服务端** `NOW(6)`：每条 DDL 前后各取一次写入 `ddl_log`，不是客户端墙钟。
- 并发探测：DDL 在后台会话执行，`sleep 8` 后从**另一个 mysql 会话**做一次主键 `SELECT` 和一次 `INSERT`，
  同样写进 `ddl_log`；同时每 20 s 采样 `information_schema.processlist`，确认当时状态是 `altering table`
  （即 DDL 确实在跑，不是已经结束才探测）。
- 顺序设计：T1→T4 逐条分解（DROP / DROP / ADD UNIQUE / ADD INDEX），T5 回滚到「V4 未跑」态，
  T6 跑 V4 原文，T7 再回滚，T8 跑 V4 + `ALGORITHM=INPLACE, LOCK=NONE`，
  T9a 造半迁移态、T9b 在半迁移态再跑 V4，T10 单独复测一次 ADD UNIQUE 并采样 `/tmp`。

## 5. 并发影响：写入没被阻塞

只取「探测时刻 DDL 仍在跑」的那些样本（T3 的探测 INSERT 因探测脚本自身 id 写死而撞主键失败，已排除，不计入）：

| 正在跑的 DDL（总耗时） | `SELECT`（主键） | `INSERT` |
|---|---|---|
| T4 `ADD INDEX`（24.6 s） | 0.001 s | 0.013 s |
| T5 回滚（38.0 s） | 0.004 s | 0.014 s |
| **T6 V4 原文（85.5 s）** | 0.001 s | **0.014 s** |
| T7 回滚（86.9 s） | 0.001 s | 0.036 s |
| T8 V4 + `LOCK=NONE`（129.5 s） | 0.001 s | **0.119 s** |

`processlist` 采样的原始片段（证明这些时刻 DDL 确实在跑）：

```
altering table|ALTER TABLE amz_order\n    DROP INDEX uk_amazon_order,\n    DR <- 20:58:10
committing alter table to storage engine|ALTER TABLE amz_order\n    DROP INDEX uk_amazon_order,\n    DR <- 20:58:50
```

**这不是推断**：`ALGORITHM=INPLACE, LOCK=NONE` 那条语句 MySQL 接受了并跑完（rc=0）——
若该 DDL 不支持在线执行，MySQL 会直接报错而不是接受。

一个必须知道的上限：并发 DML 会写入 online row log，`innodb_online_alter_log_max_size` 为 **128 MB**。
若 V4 执行期间并发写入超过它，ALTER 会失败（`DB_ONLINE_LOG_TOO_BIG`）。
本轮并发量只有几行，**没有触发，属配置读数而非实测**。

## 6. 可直接用的三条结论

1. **V4 的耗时由两个 ADD 决定，DROP 不用考虑**：`DROP INDEX` 是元数据级（0.07–0.15 s）。
   维护窗按「复合唯一键 ~40 s + 复合索引 ~25 s」这个量级估，5M 行整条 V4 实测 85.5 / 129.5 s。
2. **失败路径不耗时**：半迁移态撞 `1061` 在开始构建索引之前就被拒绝，5M 行表上 <1 s 返回，
   且原子 DDL 回滚了两个 DROP。不需要担心「启动卡住几十分钟才失败」。
3. **V4 期间读写都还在**：DML 未被阻塞（实测 0.013–0.119 s）。
   但 Flyway 是在服务启动时跑迁移的，真正风险不是锁，而是**多实例同时启动**时的相互踩踏（见 §7 未测）。

## 7. 边界与未测（不要跳过）

- **方差比精度重要**：同一台机器、同一条回滚 SQL，两次 **37.987 s vs 86.869 s（2.3 倍）**；
  同一 V4 语义 85.507 s vs 129.521 s（1.5 倍）。任何「V4 需要 X 秒」的单点数字都不可靠。
- **生产行数没有数据来源**：本地 compose 的 `amz-mysql` 里 `amz_order.amz_order` 是**空表（0 行）**，
  没有任何库能给出真实行数。5,000,000 行是**自设压力档位，不是预测**。
  按量级外推约每百万行 17–26 s，只能当量级参考，不能当 SLA。
- **磁盘**：T10 期间每 ~2.5 s 采样 `du -sm /tmp`，全程 **1 MB**，未观测到 tmpdir 溢出。
  这是「没看到溢出」，不是峰值字节数；datadir 内的 online row log 未单独测量（上限见 §5）。
- **未测**：从库/复制延迟（演练无复制拓扑）、云盘 IO 表现（这里是本地容器磁盘）、
  buffer pool 更大时的表现（本轮 128 MB，是偏保守的 IO 密集场景）、
  以及多个服务实例同时启动执行迁移时的相互作用。
- 本轮所有结果均在**本地容器**产出，CI 远端未验证。
