# 业务功能升级方案（2026-10-11，基于同类项目调研）

> **范围前提（用户拍板，2026-10-11）**：
> 1. 无真实 API 店铺数据——功能做到**拎包入住**（契约测试绿 + mock 链路完整即交付），不为「未联调」停留；
> 2. **商业化功能一律不做**（会员/积分/充值/订阅收费）——纯免费全功能项目；
> 3. 业务功能**尽可能做全**，以主流跨境电商 ERP 的功能面为对标。
>
> **调研来源**：GitHub `wimoor-erp/wimoor`（1382⭐，MIT，Java+Vue，最贴近的开源同类，
> 实测其模块树：Amazon 域 feed/finances/inbound+V2/inventory/notifications/orders/
> performance/product/profit/report/summary/transparency + 通用域 customer/finance/
> inventory/material/order/purchase/ship/stock/thirdparty/warehouse，另有 ads/quote/data 独立模块）；
> 商业产品功能面（领星官网功能页、店小秘 vs 马帮选型对比）；启航(116⭐)/提姆(84⭐) 佐证
> 「多平台订单统一 + 多仓 + 供应链流程」是赛道标配。

# 二、升级方案（四期，每期拎包入住交付）

## P1 流程闭环与地基（建议最先做；多为小改动大闭环）

1. **库存流水全面接入**（B4/B5）：调拨 approve/ship/receive、入库 receive、出库 pick/pack/ship
   接入 `InventoryMovementService`（表已就绪，改 4 个 service 的变更点 + before/after 取值）。
2. **库存盘点（A2）**：盘点单表（建单→按仓库+SKU 快照账面数→录入实盘→差异审核→按差异写流水
   `STOCKTAKE_ADJUST` 调整库存）；复用流水账与「只增不改」纪律。
3. **工单/差评挽回终态**（B1/B2）：`/{id}/close`（REPLIED→CLOSED），复用处置端点模式。
4. **角色/用户管理（A7）**：沿 ShopController 模式补 `GET/PUT /user/role`、用户列表、禁用；
   已知限制（JWT role 24h 不刷新）写进注释与页面。
5. **报表导出（A4）**：通用 CSV 导出（`produces=text/csv` 流式 + 复用现有 keyset 分页游标）；
   先做利润明细/订单/库存三个高频报表；前端下载按钮。
6. **消息中心落库（C6）**：通知表 + 历史查询端点 + 页面读历史（量小）。

## P2 订单履约与供应链补全

1. **一键配货/订单履约流**（对标 wimoor order→stock→ship）：待发货 Amazon 订单 → 按 SKU 匹配
   本地仓/FBA 渠道 → 生成配货单 → 出库扣减（接流水）→ 关联发货回传（S7.3 已有）。
   这是「订单域只读」到「订单域可履约」的最后一跳。
2. **三单匹配与供应商付款（A3）**：付款单/采购发票表 + PO-收货-发票三角校验（容差可配）+
   与 finance 凭证源端点联动；PAID 状态由付款单写入（终结「枚举有、写入无」的悬空）。
3. **批量到货/采购合同模板/打印标签**（对标领星进销存提效项）：批量 receive 端点 +
   标签打印（复用 packingSlip 的打印窗口模式）。
4. **物料/BOM（组合装）**：material 表（组合品→子品数量关系）；出库按 BOM 展开、成本按子品归集。
   影响面大，先做「纯报表层组合品视图」还是「库存层真 BOM 扣减」需一次产品拍板。

## P3 运营工具补全与账号健康

1. **店铺绩效域（对标 wimoor performance）**：SP-API `accountHealth`（ODR/迟发率/取消率）
   + `GET_V2_SELLER_PERFORMANCE_REPORT`；新增 amz_shop_performance 表 + 看板页 +
   阈值告警（复用现有告警处置闭环）。数据源就绪度同 SP-API 主链路（拎包入住）。
2. **Listing 自动调价**（对标领星）：调价规则表（跟卖触发/竞品价差/定时）+ listingsItems
   PATCH 执行（API-ready 已就绪）+ 规则执行日志。与现有广告分时调价（BidSchedule）并列成
   「两个真实改价通道」。
3. **Review 星级统计**：订单域已有差评告警骨架；补「按 ASIN 的 1-5 星分布+评论率」报表
   （数据源：客户退货报表之外的 review 报表或 Keepa，等凭据；先落表结构与 mock 链路）。
4. **竞品上新监控**：Keepa 客户端已就绪，加「竞品 ASIN 变动扫描→通知」调度（等 token，mock 先行）。

## P4 AI 自动化与平台扩展（本仓差异化）

1. **AI 广告托管**（对标领星 AI 广告托管）：把现有 29 工具 Agent 的
   `optimize_ad_campaign`/分时调价升级为「目标→Agent 规划→执行→回看」的托管循环；
   执行层复用真实改价通道，**必须带干跑/审批门槛**（写操作工具已有 OPERATE 权限模型）。
2. **AI Listing 内容**：标题/卖点生成（DeepSeek 已接）+ 图片生成（外部凭据）；落 listing_seo 表已有。
3. **平台适配层抽象（A8 前置）**：把 Temu/TikTok/Shein 三个 client 的公共形状（orders/products/
   messages/inventory/webhook）提为 `PlatformAdapter` 接口 + 注册表；新平台 = 一个 client + 注册
   （对标 wimoor 20+ 平台、马帮 100+ 平台的扩展姿势）；随后多平台订单并入统一报表（A8）。
4. **外观专利检索** ➖（领星特色，依赖专利数据库源；列为观察项，不承诺）。

# 三、执行纪律（沿既有约定）

- 每项仍走 TDD 先红后绿 + 契约锁 + 门禁同步（迁移钉数/失败出口/fallback 计数等）；「拎包入住」
  指不追求真实联调，**不降低**工程门禁标准。
- 新表沿用迁移规范（V 序号、状态机注释、唯一键、shop_id 隔离列）；新端点沿用
  `@ShopScoped/@RequireRole/@OperLog`（覆盖契约会强制后者）+ 服务层归属校验。
- 调度类默认关闭 + 显式店铺清单 + `DistributedJobLock`（沿 AmazonReturnSyncScheduler 先例）。
- 商业化功能（会员/积分/充值/订阅）**不做**；若未来要做，属新立项而非本计划。
- 每期完成后刷新 HANDOFF 并按交班纪律收口。

# 四、规模与顺序建议

| 期 | 内容 | 量级 | 为什么是这个顺序 |
|---|---|---|---|
| P1 | 流水接入/盘点/工单终态/角色管理/导出/通知落库 | 中（多为小改动） | 地基类：流水与角色是后面所有项的依赖 |
| P2 | 配货履约流/三单匹配/打印标签/BOM | 大 | 供应链闭环；BOM 需一次产品拍板 |
| P3 | 店铺绩效/Listing 调价/Review 统计/竞品监控 | 中 | 数据源多为 SP-API/Keepa（拎包入住） |
| P4 | AI 广告托管/平台适配层/AI 内容 | 中大 | 差异化收尾；平台适配层是 A8 的前置 |
