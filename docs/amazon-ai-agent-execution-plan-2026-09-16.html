T15Supervisor-Worker 多 Agent 编排
P0AI依赖决策

为什么：两个理由。功能上，29 个工具已可按域分组，单 Agent 全量携带会让工具选择变差；口径上，面试表述里的 Supervisor-Worker 目前在本项目没有实现（代码唯一命中是一个名为 workers 的线程池）。

前置
Wave 0 决策必须已定（见第 08 节）
动作
  1. 把 29 个工具按域分组：财务 / 广告 / 物流 / 选品 / 客服 / 知识库，每组对应一个 Worker。
  2. 实现 Supervisor：任务分类 → 复杂度评分 → 拆分 → 路由到 1..N 个 Worker → 结果聚合。
  3. Worker 只携带本域工具，降低误调用；跨域任务由 Supervisor 并行下发后合并。
  4. 沿已有 AgentToolEventBus 输出各 Worker 的执行时间线，SSE 流式保留。
  5. 权限沿用 ToolPermission：Worker 不得拿到超出其域的工具。
涉及
agent/ 新增 supervisor/ 与 worker/ 包；ErpToolExecutor、AgentChatStreamService
验收：跨域问题（如「这个 SKU 利润为什么掉了」）能被拆分到财务 + 广告两个 Worker 并正确聚合；单域问题不走多 Agent 路径（避免无谓开销）；每个 Worker 只能调用本域工具，越域调用被拒绝。

08唯一需要先决策的事项

决策项：Supervisor-Worker —— 补实现还是改口径？
现状：面试口径提到 Supervisor-Worker，但本项目代码中并未实现多 Agent 编排。检索 supervisor / worker / orchestrat 的唯一命中，是 AgentChatStreamService 里一个名为 workers 的线程池。这是容易被追问、一问就穿的表述。
  • 方案 ①「补实现」（推荐）：执行 T15。功能上本就受益（29 个工具按域收敛，降低误调用），且经验记忆（T11–T14）与编排天然互补。做完这一项，口径与代码就一致了。
  • 方案 ②「改口径」：把本项目表述改为「单 Agent ReAct + 29 工具 + 工具级权限治理 + RAG 知识库 + LLM 评估双轨」，把 Supervisor-Worker 明确划到智云项目去讲。同时可删掉 T15，Wave 2 缩短为 6 项。
不建议保持现状含糊处理 —— 这是三种做法里风险最高的。
同时记住「不该做什么」。 亚马逊原生 AI 已免费覆盖：Listing 与 A+ 的文案生成（卖家采纳率约 90%）、AI 素材生成（Creative Studio 图 / 视频 / 音频）、基础关键词建议。这三类自研是重复造轮子，且质量比不过平台原生工具。本方案的 28 项任务里刻意没有包含这些 —— 补能力的判断标准始终是：亚马逊原生 AI 会不会做？会做的就不做。
